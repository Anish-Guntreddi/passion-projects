# Benchmark methodology

Status: **no benchmark runs have been executed yet.** `benchmarks/traces/`
and `benchmarks/raw/` and `benchmarks/plots/` are placeholders
(`.gitkeep` only) until Phase 7 ("Benchmark study" in the roadmap). This
document records the methodology now so it is designed before any numbers
exist, per agent execution rule #4 ("never fabricate performance
numbers") — the plan is written first; results get committed only once
they are real.

## What Phase 1 already demonstrates (not a formal benchmark)

`examples/phase1_fragmentation_demo.py` and
`tests/unit/test_contiguous.py` already produce real, reproducible
numbers for the Phase 1 exit criterion ("variable-length trace
demonstrates fragmentation/waste numerically") using
`ContiguousMemoryModel`. These are deterministic simulation outputs, not
wall-clock benchmark results, and are not written to `benchmarks/raw/` —
that directory is reserved for Phase 7's committed, methodology-governed
results.

## Planned workloads (spec S1.8)

Reproducible synthetic traces via `minipaged.simulation.trace.generate_trace`,
committed under `benchmarks/traces/` once frozen (a trace is
`(TraceConfig, seed)` — the config and seed are what's actually committed
and reproducible; the materialized `TraceRequestSpec` list is regenerated
from them, not hand-edited):

- **Uniform** — narrow `prompt_len_range` / `max_new_tokens_range`, no
  early completion (`completion_fraction_range = (1.0, 1.0)`).
- **Mixed short/long** — wide `max_new_tokens_range`.
- **Burst arrivals** — `mean_interarrival` near 0, or several requests at
  `arrival_time = 0.0`.
- **Shared-prefix** — requires Phase 4 (prefix sharing); not runnable
  until then.
- **Memory-pressure** — `capacity_tokens` sized so the trace's aggregate
  worst-case reservation exceeds capacity, exercising admission
  rejection/queuing.
- **Decode-heavy vs. prefill-heavy** — varying the prompt-length-to-
  max-new-tokens ratio.

## Planned metrics (spec S1.8)

TTFT; inter-token latency / time-per-output-token; requests/sec and
tokens/sec; queue delay; active sequences; KV physical capacity / used
tokens / reserved capacity / utilization; allocation failures /
preemptions; fragmentation/waste for the contiguous baseline (available
today via `ContiguousMemoryMetrics` — the rest require a real scheduler
(Phase 3) and/or real model (Phase 5) to be meaningful, since Phase 0-1
has no wall-clock cost model at all: `SimClock` ticks are abstract units,
not measured latency).

## Reporting rules

- Every committed result under `benchmarks/raw/` is JSON, generated by a
  script under `benchmarks/` (not hand-written), with the exact
  `(TraceConfig, seed)` and code commit it was produced from.
  `benchmarks/plots/` is generated from `benchmarks/raw/` by matplotlib,
  never hand-drawn.
- Contiguous-vs-paged and static-vs-continuous-batching comparisons
  (Phase 7) always run the *same* trace through both, exactly like
  Phase 1's own fragmentation demo already does for contiguous alone —
  see `docs/kv-memory.md`.
- No number is reported before the phase that makes it meaningful exists
  (see `docs/decisions/0002-contiguous-baseline-simulated-capacity.md`
  for why Phase 1-2's "token slots" are not real GPU bytes until Phase 5
  supplies a real per-token KV footprint).
